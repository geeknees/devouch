## 参考になる点

この事例は、別々の人間・組織に属するエージェントが、GitHub の Issue と PR を介して仕事を受け渡すシナリオとして参考になる。

[Hono-kun の図](hono-kun-reference.md)では、外部 PR を評価し、問題が実在すればプロジェクト側のエージェントが代替実装を作成していた。今回の事例では、報告側もエージェントであることから、双方の委任関係を分けて考える必要がある。

| 段階 | 想定する活動 | Devouch で検討する事項 |
|---|---|---|
| 問題の報告 | 報告側エージェントが調査して Issue を作る | 調査・外部投稿が誰から委任されたか |
| 報告の受理 | 修正側が問題と対応方針を判断する | 外部報告と、自組織の対応承認を区別できるか |
| 修正の作成 | 修正側エージェントが PR を作る | 変更が誰の委任に基づくか |
| レビュー | 人間または既存のレビュー体制で確認する | 委任・Git 来歴の検証結果を確認できるか |

Issue 作成の委任まで扱うかは、Devouch の対象範囲として別途判断する。

## 設計上の境界

### 委任は組織ごとに独立する

外部エージェントから報告を受け取っても、そのエージェントに自組織のリポジトリを変更する権限を与えたことにはならない。

報告側の委任が検証できても、その権限を修正側へ引き継ぐ根拠にはならない。修正側には、自組織の責任者による別の委任が必要になる。委任はタスクごとの指示か、継続的な権限付与かを明確にする。

### 成果物の参照と委任の証明を分ける

Issue → PR → コミットの参照関係は、作業の経緯を追う材料になる。ただし、リンクがあるだけでは人間の委任を証明できない。

また、委任・来歴を検証できても、報告の正しさ、修正の品質、マージの妥当性は別途判断が必要である。

### 検証情報がない報告も受け付けられるようにする

外部の貢献者が Devouch を利用していない場合でも、問題提起の価値は評価できる必要がある。検証情報の欠如だけで、不審・低品質と判定しない。

## 関係者への影響

以下は運用上の想定であり、参考事例で確認された当事者の見解ではない。

- **メンテナー**：調査・修正の負担軽減が期待できる一方、自組織のエージェントが動く条件と責任範囲を把握する必要がある。
- **報告者**：問題の解決と貢献の認知を期待する。修正を別のエージェントが担当しても、元の Issue への参照やクレジットを残したい。
- **レビュアー**：誰の委任による変更かを確認できる利点がある一方、検証成功を品質保証と誤解しない表示が必要になる。

## 小さな検証案

1. 外部からのバグ報告を入力として扱う。
2. 修正側の人間が、自分のエージェントへ修正を委任する。
3. エージェントが元の Issue を参照する PR を作成する。
4. Devouch で修正側の委任と Git の来歴を検証する。
5. レビュアーが検証結果と変更内容を確認する。

最初に既存機能で表現できる範囲と不足点を整理する。報告側の委任の検証、組織間の自動交渉、自動マージは別の検討事項とする。

## 未決事項

- Issue と委任の関係を、単なる参照として扱うか、検証対象に含めるか。
- 継続的な委任の場合、適用範囲と失効をどう扱うか。
- 検証情報なし・検証失敗・検証成功をどう表示するか。

## Moltbook の扱い

ユーザー提供の説明にある Moltbook は、エージェント同士の会話・交流の参考候補である。ただし、今回の説明だけでは、委任に基づく開発作業や Git の成果物との関係は確認できないため、本メモの主な検証対象には含めない。
