## 企画の核

AI によってコードの提出が容易になる一方、変更を理解し、評価し、引き受けるメンテナーの時間は有限である。

Devouch は、PR に対して誰が、何を引き受けているのかを確認できる道具を作る。PR の品質を自動で保証するのではなく、レビューへ進む判断に必要な信頼の根拠を提供する。

オリジナルの vouch を尊重し、ブロックチェーンを使って検証可能性と運営者からの独立性を高める。原典との具体的な関係は、参照リポジトリの確認後に明記する。

## 確定している制約

- Building from Scratch に参加し、ハッカソン向けに新規実装する。
- 開発者は1名。コーディングエージェントを利用する。
- 実装8時間、提出素材4時間、ピッチ準備・本番4時間。
- Ruby CLI を中心にする。
- World「Best Use of World ID for Agents」と ENS「Best Use of ENSv2」を狙う。
- Continuity 限定の ENS 賞は対象外。
- 事前コードの利用可否と、許される技術検証の範囲はイベント規約を確認する。

## 誰の、どの判断を支えるか

主な利用者は、外部から PR を受け取る OSS メンテナーである。

メンテナーが知りたいのは、単に人間が関与したかではない。誰が変更を引き受け、その人を自分のプロジェクトが信頼してよいと判断しているかである。

貢献者にとっては、AI を利用しても、自分の関与を明示して提案できることが価値になる。エージェントにとっては、人間による委任と成果物の関係を機械的に検証できることが価値になる。

Devouch を使っていない投稿者も、通常のレビュー経路を利用できる設計を基本案とする。未検証を悪質と同義にしない。

## 提案した主張の単位：採用未決定

最初の案では、次の一つに絞ることを提案した。

> 私は、この PR のこの時点の変更を、自分が引き受ける提案として提出する。

「引き受ける」はプロダクト上の意思表示であり、法的責任の保証を意味しない。また、次の主張とは区別する。

- コードの全行をレビュー済みである。
- バグや脆弱性がない。
- プロジェクトが採用・マージを承認した。
- エージェントへの事前委任があった。

事前委任だけでは、最終的に提出された変更を人間が引き受けたことまでは分からない。そのため、PR の特定の head commit に対する意思表示を中心にする案とした。

ただし、信頼の入口として貢献者を推薦する仕組みと、個別成果物の来歴は別である。原典の vouch と既存のプロジェクト方針に照らして、この案を見直す必要がある。信頼履歴を毎回ゼロから作り直す設計にはしない。

## この案を採用した場合の利用フロー

1. 人間またはエージェントが、PR に対する意思表示の要求を作成する。
2. 人間が対象リポジトリ、PR、head commit、主張の内容を確認する。
3. World ID for Agents のフローを完了する。
4. バックエンドが World の結果を検証し、対象の要求に結びつける。
5. 人間の署名など、第三者が検証できる方法で意思表示を記録する。
6. Ruby CLI が記録と現在の PR を照合する。
7. メンテナーに検証結果と、プロジェクトの信頼方針への適合を表示する。

World の結果と署名者をどう結びつけるかは、公式仕様の確認が必要である。ウォレット接続だけで対応関係が証明されたとは扱わない。

新しいコミットが追加された場合、過去の意思表示は過去の状態に対する記録として保持し、現在の PR を確認済みとは表示しない。

## 各要素の役割

| 要素 | 役割の案 | 保証しないもの |
|---|---|---|
| World ID for Agents | 意思表示の発行時に人間の確認を要求する | GitHub の権限、コード品質、署名者との自動的な同一性 |
| ENSv2 | プロジェクトが管理する名前空間と役割を表現する | 世界共通の信用、GitHub の操作権限 |
| Ruby CLI | 主張・対象コミット・権限・プロジェクト方針を検証する | コードの正しさやマージ判断 |
| 小さな Web／バックエンド | 人間による確認と World の安全な検証を担う | 単独で全利用者の信用を決定すること |

### ENSv2 の採用候補

プロジェクトが管理する名前空間に意思表示を行う主体を登録し、管理者と各主体の権限を分ける。

- 管理者は、登録や権限の付与・取り消しを管理する。
- 各主体は、許可された自己情報のみ変更できる。
- CLI は、プロジェクトが選んだ名前空間と方針を参照する。

ENS のレコード編集権限と、PR を推薦する資格は同じではない。対応づけるアプリ側のルールを明示する。具体的なロール・レコード構成と、プロジェクトをまたぐ再利用の方法は未決定。

## 公共インフラとしての設計原則案

- 各プロジェクトが信頼する主体と受け入れ方針を選ぶ。全体共通の信用スコアは作らない。
- 記録形式と検証方法を公開し、ホストされた画面だけに依存しない。
- 署名が有効でも、プロジェクトがその主体を信頼しているとは限らない。
- 現在の権限を失ったことと、過去に行った意思表示を区別する。
- PR・登録・推薦の件数に応じたトークン報酬やランキングを導入しない。
- 個人情報、コード本文、生の認証結果を不用意にオンチェーンへ残さない。

Tea の事例は未確認である。「活動量への報酬が不要な投稿を誘発し、メンテナーへ負担を転嫁しうる」という懸念は、記事に基づく事実認定とは分ける。

ブロックチェーンを利用するだけで全体が分散化されるわけではない。World、GitHub、RPC、バックエンドへの依存を明示する。

## この案の最小デモ

1. 未確認の PR について、CLI が信頼根拠の不足を示す。
2. 人間が対象を確認し、World のフローを完了する。
3. CLI が、その commit に対する意思表示とプロジェクト方針への適合を示す。
4. PR にコミットを追加すると、現在の変更は未確認と表示される。
5. World のキャンセル時には、意思表示が発行されない。
6. ENSv2 の権限外操作が拒否される。

検証成功の一語にまとめず、記録自体の検証結果、対象コミットとの一致、プロジェクトが信頼する主体か、現在確認できない事項を区別する。

## 実装前に解消する論点

| 論点 | 必要な確認 | 解消できない場合 |
|---|---|---|
| World の利用 | イベント用環境、成功・失敗の検証方法 | 賞を満たしたとは扱わず、対象を見直す |
| 第三者による検証 | 外部 CLI が何を検証できるか | サーバーを信頼する部分を明示する |
| 署名者との対応 | World の確認、要求、署名鍵の結びつけ方 | 単なる併記で本人性を主張しない |
| ENSv2 の中心的用途 | 名前空間と権限が CLI の判断に使えるか | 用途または応募方針を再検討する |
| Ruby との接続 | 署名・チェーン照会の既存実装 | 必要最小限の補助コンポーネントを検討する |
| イベント規約 | 新規開発の範囲、事前準備、併願条件 | 実装開始前に計画を修正する |

暗号処理は既存ライブラリを利用し、独自実装しない。オンチェーン記録と署名済みオフチェーン記録の分担は未決定で、両方式を最初から実装する計画にはしない。

## 作業と提出

8時間の実装、4時間の提出素材、4時間のピッチの配分は [統合版の計画](hackathon-planning.md) に従う。

World の初回成功までの時間と改善フィードバックは実装中から記録する。変更する振る舞いはテストを先に用意する。コーディングエージェントには各タスクの入出力・変更範囲・完了条件を渡す。

ピッチのメッセージ案：

> AI はコードを増やせる。メンテナーの信頼と時間は増やせない。Devouch は、PR を誰が引き受けているかを、プロジェクト自身が検証できるようにする。

原典の確認後、信頼の対象と採用する主張に合わせて表現を更新する。
