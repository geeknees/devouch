# AI エージェント管理者向け：Devouch を使った PR 送信マニュアル

更新：2026-09-26。推薦版のCLI・静的画面・Actionを実装しました。検証範囲は [実装状況](implementation-status.md)を参照してください。repoとPagesの公開、固定Actionの匿名取得、[推薦付き実fork PR](demo-evidence.md#masusanouの実fork-pr)のvalid / acceptedを確認済みです。デモ先は `geeknees/devouch`、送信者は `masusanou`（数値ID `287365775`）です。失効のPR検証と人間名義の実PR検証はユーザー指定で今回の対象外です。[実機手順](demo-runbook.md)もこの範囲に合わせています。

対象は、AI エージェントに変更を作らせ、OSS リポジトリへ PR を送る管理者です。**管理者本人の GitHub アカウントで送る場合と、AI エージェントが持つ専用の GitHub アカウントで送る場合の両方**を扱います。

この案で管理者が行う追加作業は、**実際に PR を送るアカウントへの推薦を受け取り、最初の PR に推薦 JSON を含め、検証結果を読むこと**です。

管理者やエージェントが投稿前に取得・検証する場合は [CLI の操作案](cli-interface.md#4-取得と検証を直接使う)を参照してください。CLI の直接導入は任意で、推薦を受け取って Action の結果を確認する以下の手順では必須にしません。

## 二つの送信名義と推薦の対象

このマニュアルは、PR 作者のアカウントへ直接推薦を付ける案で両方の手順を整理しています。以下の ID は説明用です。

| 送信名義 | 推薦を受ける対象 `subject` | PR に含める推薦ファイル |
|---|---|---|
| 管理者本人のアカウント | 管理者の `github:12345` | `.devouch/vouches/github-12345.json` |
| エージェント自身の専用アカウント | エージェントの `github:67890` | `.devouch/vouches/github-67890.json` |

後者では、エージェントのアカウント自体への推薦を受けます。管理者への推薦が自動で引き継がれるわけではありません。管理者とエージェントの関係の証明、および共有の GitHub App の扱いは [後半](#管理者との関係と-github-app)のレビュー事項です。

## 最初の PR までの流れ

| 手順 | 管理者が行うこと | エージェントに任せられること | 完了の目印 |
|---|---|---|---|
| 1. 投稿先と名義を確認 | PR を送る repo とアカウントを決める | 投稿先の案内と設定を調べる | 推薦を受ける GitHub ID が決まる |
| 2. 推薦を受け取る | 投稿先が受け入れる推薦者へ依頼する | 依頼に必要な公開情報を整理する | 公開済みの推薦 JSON が手元にある |
| 3. 作業を依頼する | 作業範囲・送信名義・推薦ファイルを指定する | 実装、テスト、推薦 JSON の配置、PR の準備・送信 | PR の差分に必要な推薦が含まれる |
| 4. 結果を確認する | 採否と理由を確認し、レビューに対応する | Action の結果を読み、問題を切り分ける | 対象アカウントの検証結果を確認できる |

通常の開発環境と PR 送信に使う GitHub の認証・権限は必要です。Devouch のために管理者やエージェントがウォレットを用意したり、PR ごとに署名・ガス支払いをしたりする手順はありません。推薦を発行する人が署名と公開を担当します。

## 1. 投稿先と PR の送信名義を確認する

投稿先のベースブランチで、次の二つを確認します。これは受け入れ側のメンテナーが用意するものです。

- `.devouch/policy.json`：受け入れる推薦者と用途。
- `.github/workflows/devouch.yml`：PR 作者の推薦を検証する workflow。

導入されていなければ、その repo では Devouch による結果表示を利用できません。導入の相談には [受け入れ側メンテナー向けマニュアル](adoption-guide.md)を使います。自分の PR だけで受け入れ条件を緩めることはできません。

次に、実際に PR 作者になるアカウントの数値 ID を確認します。`PR_AUTHOR_LOGIN` を管理者本人またはエージェントの送信アカウントのログイン名に置き換えます。GitHub CLI を利用している場合の読み取りコマンドです。

```bash
gh api 'users/PR_AUTHOR_LOGIN' --jq '{login, id}'
```

返された `id` が `12345` なら、推薦対象は `github:12345`、`67890` なら `github:67890` です。これは表示名や commit の author 名ではありません。GitHub CLI を使わない場合は、GitHub の公開ユーザー API から同じ `id` を確認できます。[ユーザー API](https://docs.github.com/en/rest/users/users#get-a-user)、[gh api](https://cli.github.com/manual/gh_api)

管理者がエージェントを起動しても、PR 作者がエージェントのアカウントなら、推薦対象はエージェント側の ID です。推薦の依頼前に、使用する PR 送信名義を確認します。

## 2. 推薦者から公開済み JSON を受け取る

投稿先が受け入れている推薦者に、対象アカウントへの推薦を依頼します。管理者本人への推薦か、エージェントのアカウントへの推薦かを伝えます。誰に依頼できるかは、投稿先の README / CONTRIBUTING の案内で確認します。連絡先がない場合はメンテナーへの確認が必要です。中央の推薦者検索サービスは、この案にはありません。

依頼文の例です。送信は管理者が通常使っている連絡経路で行います。

```text
AI エージェントを使って OSS に貢献するため、Devouch の推薦をお願いしたいです。

送信名義: <管理者本人 / エージェント専用アカウント>
対象アカウント: https://github.com/<PR_AUTHOR_LOGIN>
対象 GitHub ID: github:<PR 作者の数値 ID>
用途: oss-contribution
これまでの協働・貢献: <推薦を判断してもらうための公開リンクや説明>
利用予定の repo: <OWNER/REPOSITORY>

推薦いただける場合は、用途と期限を確認したうえで、
ENS へ公開済みの推薦 JSON を受け取りたいです。
```

利用予定の repo は依頼の背景です。推薦自体は特定 repo に固定せず、他の repo でも同じものを評価できる形式です。推薦者は依頼を受けるか、用途・期限をどうするかを自分で判断します。

公開済みの `github-<PR 作者の数値 ID>.json` と、対象・推薦者・用途・期限の説明を受け取ります。管理者の例なら `github-12345.json`、エージェントの例なら `github-67890.json` です。静的画面の公開・取得後に、Download endorsementからその名前でダウンロードできます。取得時にウォレットの接続は不要です。現在の有効性と投稿先の方針は、PR 先の Action が検証します。

| 受け取る情報 | 確認すること |
|---|---|
| 対象 `subject` | 実際に PR を送るアカウントの ID と一致する。例では管理者が `github:12345`、エージェントが `github:67890` |
| 推薦者 `issuer` | 投稿先が受け入れる推薦者のアドレスである |
| 用途 `scope` | 例では `oss-contribution`。投稿先の方針と一致する |
| 有効期限 `expiresAt` | 利用予定の時点で期限内である |
| ファイル | 本文と署名を含む、公開済み推薦 JSON の完全なコピーである |

推薦 JSON は内容を編集・整形せず保存します。対象や期限が違っていたら、自分で書き換えず、推薦者へ修正した内容での再発行を依頼します。JSON の構造は [データ構造の説明](hackathon-data-model.md#3-公開する推薦の構造)を参照してください。

GitHub ID と推薦関係は公開され、失効しても過去の公開履歴は残ります。推薦を依頼する段階で、この公開範囲を理解して進めます。

## 3. エージェントへ作業を依頼し、推薦を PR に含める

エージェントに、いつもの作業依頼に加えて PR の送信名義と、そのアカウントに対応する推薦ファイルを渡します。初回は作業ブランチへ次のファイルを追加します。`<PR 作者の数値 ID>` を、今回使う ID に置き換えます。

```text
.devouch/
  vouches/
    github-<PR 作者の数値 ID>.json
```

`policy.json` と workflow は受け入れ側が管理する設定を使います。推薦ファイルは署名済みの公開データなので、エージェントへそのまま渡せます。推薦者の秘密鍵は受け取りません。

以下は両方の送信名義で使える指示文です。`<...>` を今回の作業に置き換え、`AUTHOR_ID` はすべて同じ PR 作者の数値 ID にします。管理者の例は `12345`、エージェントの例は `67890` です。

```text
対象 repo: <OWNER/REPOSITORY>
作業内容: <Issue URL または具体的な変更内容>
PR 送信名義: <管理者本人 / エージェント専用アカウント>
PR 送信アカウント: <GitHub ログイン名>
PR 作者の GitHub ID: github:<AUTHOR_ID>
推薦ファイル: <受け取った JSON のローカルパス>

repo の AGENTS.md と貢献手順に従い、指定した変更と必要なテストを行ってください。
PR の作成・更新は、今回の作業で許可した範囲と送信名義で行ってください。

Devouch の扱い:
- 初回の PR には、推薦ファイルを .devouch/vouches/github-<AUTHOR_ID>.json に含める。
- 同じ公開済み推薦が既にあれば、そのファイルを使う。
- 推薦本文・署名は変更せず、自分の判定を通すために policy や workflow を変更しない。
- 指定した送信名義で PR を作成できない場合は、その事実を報告する。

PR の説明には、解決する問題・変更内容・実行したテストを記載する。
投稿先が AI 利用の説明を求める場合は、その方針に従う。
作成後は、実際の PR 作者と Devouch Summary の対象が一致するか確認し、
証拠の状態、repo の採否、失敗していれば理由を報告する。
検証していないことを、確認済み・人間承認済みと記載しない。
```

この指示文は作業指示です。管理者からエージェントへの暗号的な委任証明にはなりません。今回の推薦中心の版が確認するのは PR 作者への推薦です。

その後の commit・push・PR 作成は、管理者が許可した通常の開発手順で行います。Devouch 専用の commit コマンドや、PR ごとの推薦再発行は求めません。

## 4. PR 作者と検証結果を確認する

PR を開いたら、投稿先のチェックから `Devouch endorsement report` の実行と Summary を開きます。以下はエージェント自身のアカウントが PR 作者になる場合の表示例です。管理者名義の例なら対象は `github:12345` になります。

```text
対象: github:67890
証拠の状態: valid
repo の採否: accepted
推薦者・用途・検証時刻: <今回の検証結果>
人間性の確認: 含まれていない
```

これは表示例です。成功の目印は、対象 ID が実際の PR 作者と一致し、証拠が `valid`、repo の採否が `accepted` であることです。最小版は結果表示用なので、workflow の緑色だけでは推薦が受け入れられたと判断できません。マージの判断はメンテナーが行います。

PR 作者を調べる読み取りコマンドの例です。`OWNER`、`REPOSITORY`、`PR_NUMBER` を実際の値へ置き換えます。

```bash
gh api 'repos/OWNER/REPOSITORY/pulls/PR_NUMBER' --jq '.user | {login, id, type}'
```

Devouch はこの PR 作者の数値 ID を対象にします。エージェントを起動した人、CI を再実行した人、commit の author とは区別します。[PR 取得 API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)

| 結果・症状 | 管理者が確認すること |
|---|---|
| `missing` | 投稿先の PR に、PR 作者の ID に対応する JSON が含まれているか。推薦者が ENS へ公開したか |
| `invalid` | PR 作者と推薦対象が一致するか。受け取った JSON を変更していないか |
| `valid / rejected` | 推薦者・用途が投稿先の方針を満たすか。受け入れ条件をメンテナーに確認する |
| `expired` | 推薦者へ更新を依頼し、新しく公開された JSON で対象アカウントのファイルを更新する |
| `revoked` | 推薦者が撤回した推薦。古い JSON の再送では解消しない。推薦者に確認する |
| `unavailable` | 接続や履歴取得の問題。再実行できなければメンテナーへ依頼する |
| チェックがない | 投稿先の導入状況、fork の実行承認、PR の競合を確認する |

推薦を確認できなかったことだけで、投稿した変更が悪質だと判定されるわけではありません。変更内容については通常のレビューに対応します。

## 次の PR・別の repo・運用の終了

| 状況 | Devouch で追加する作業 |
|---|---|
| 同じアカウントで同じ repo に次の PR | 推薦が取り込み済み・有効なら追加作業なし。各 PR で現在の状態を再検証する |
| 同じアカウントで別 repo に初めて PR | その repo の受け入れ方針を確認し、同じ JSON を追加する。再署名・再公開は不要 |
| 同じ送信アカウントでモデルや実行環境を替える | 現在の推薦はモデルに紐づかないため、自動では失効しない。運用の変更で推薦の前提が変わる場合は推薦者と見直す |
| 管理者名義とエージェント名義を切り替える | 切り替え先のアカウントへの推薦と、その ID の JSON が必要。既に有効な推薦があれば再利用できる |
| エージェントを停止する | 実行環境と GitHub の操作権限を管理者側で止める。推薦の失効とは別の操作 |
| 推薦を取り消してもらう | 推薦者へ失効を依頼する。Git のファイル削除だけでは、他 repo でも使える推薦の失効にならない |

## ブロックチェーンが担当すること

推薦者は本文と署名を ENSv2 に公開し、撤回するときも ENS を更新します。各 repo の Action は、手元の JSON と同じ公開記録・更新履歴を参照します。そのため、古い JSON が各 repo に残っていても、次の検証で失効を確認できます。GitHub の過去のチェック表示は、自動では更新されません。

どちらのアカウント名義でも、通常の PR を送る際の操作は GitHub 上で完結し、ブロックチェーンへの書き込みは発生しません。推薦者が発行・失効のガスを負担し、検証には RPC の読み取り接続を使います。Devouch 運営者による発行許可や中央アカウント登録は不要です。[保存先と役割の説明](adoption-guide.md#ブロックチェーンの役割)

## 管理者との関係と GitHub App

エージェント自身への推薦と、「誰がそのエージェントを管理しているか」の証明は別です。このマニュアルの案では、前者を PR 作者の ID への直接推薦として扱います。

| 確認したいこと | この案での扱い |
|---|---|
| 管理者名義の PR 作者への推薦 | 管理者アカウントを対象にした署名済み推薦を検証する |
| エージェント名義の PR 作者への推薦 | エージェントのアカウントを対象にした署名済み推薦を検証する |
| エージェントの管理者・操作を許可した人 | 推薦 JSON の形式には、その関係を証明する情報がない。委任等の設計が別途必要 |
| 管理者の信用をエージェントへ引き継ぐ | 直接推薦だけでは行わない。引き継ぎの条件と検証方法はレビュー事項 |

管理者自身が投稿先から受け入れられている推薦者なら、推薦者としてエージェントのアカウントへ推薦を発行することも、この直接推薦の案に含まれます。管理者であるという理由だけで、その repo が推薦を受け入れるわけではありません。この場合の推薦も、管理関係や個別の作業委任を証明するものではありません。

エージェントの専用アカウントと、GitHub App に付属する Bot アカウントは区別します。GitHub App は installation token で App の Bot として操作する場合と、user token でユーザーに代わって操作する場合があります。利用ツールの名前から PR 作者を推測せず、実際の PR 作者で確認します。[GitHub の認証とアカウントの説明](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)

現在の検証対象は PR 作者の ID だけなので、同じ App の Bot を使う管理者や導入先を、その ID から識別する設計にはなっていません。PR 本文の「この Bot の管理者です」という自己申告も、委任証明には使いません。

専用アカウントへの直接推薦で目的を満たすか、管理者との関係や作業単位の委任も必要かをレビューします。共有の App の Bot に対する推薦を、その利用者全員への推薦と読み替えません。

## このマニュアルでレビューする点

| 論点 | 現在の案で見えている負担・制約 |
|---|---|
| 誰への推薦が必要か | 管理者名義とエージェント名義の両方で、実際の PR 作者のアカウントを直接推薦する案 |
| 管理者との関係も必要か | エージェント自身への推薦だけでは、管理者の特定や管理者からの委任は証明できない |
| 推薦を頼めるか | 投稿先が受け入れる推薦者への依頼が必要。案内・連絡先がなければここで止まる |
| 初回の追加作業は許容できるか | 推薦 JSON を受け取り、repo ごとに初回 PR へ1ファイル追加する |
| エージェントに任せられるか | ファイル配置・通常の開発・結果確認を任せる。推薦の判断は推薦者、受け入れ方針はメンテナーが持つ |
| 結果は十分か | PR 作者の推薦を確認する。人間性、管理者の個別 PR 承認、エージェントへの委任、コード品質は証明しない |
| 複数アカウントへ展開できるか | 管理者とエージェントの双方へ同時に推薦を保つ場合も、現行の一記録・一推薦のデモ案では不足。独立した公開先の設計が必要 |

本文では両方の送信名義の使い方を説明していますが、2026-09-26のユーザー指定により、今回の実PRデモはmasusanou名義の有効な推薦の確認までとします。人間名義の実PR検証と失効後のPR再実行は行いません。二つの推薦を同時に保つ機能ができたとは扱いません。

配布画面とActionの公開、エージェント名義の実PRでの有効推薦は確認済みです。管理者とエージェントの関係を検証する機能を追加するかは、レビュー後に判断します。
