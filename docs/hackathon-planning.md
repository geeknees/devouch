## 1. 目的

**AI slop の時代に、PR の信頼性を判断するための公共インフラを作る。**

オリジナルの vouch を尊重し、ブロックチェーンを活用して分散性を高める。メンテナーの負担を増やすインセンティブ設計を避け、特定の運営者に依存しすぎないツールを目指す。

友人であり Hono の開発者でもある yusukebe が AI Slop に悩まされていたことも、ユーザーの動機の一つである。[本人の記事](https://zenn.dev/yusukebe/articles/3fd5bc6ea341c9)を参照し、メンテナーの時間と、貢献者を受け入れられる関係を守ることを目指す。Hono / yusukebe による Devouch の採用・推薦を意味するものではない。

今回の MVP は、**貢献者への推薦の発行・失効・再利用**を中心にする。人間であること、貢献者への推薦、エージェントへの委任、コードの品質は同一視しない。

賞への適合より分散性を優先する。ENSv2 を使う基本構成を先に成立させ、World賞は運営者への依存を増やさず両立できた場合に狙う。

### 既存のプロジェクト方針

保存時に確認した [gotchas.md](../gotchas.md) では、無関係な OSS リポジトリ間でも信頼履歴を再利用できることを中核要件としている。最終的な判断権は各リポジトリの方針に置きつつ、貢献者がプロジェクトごとに信頼履歴を作り直さずに済む、共有台帳に記録可能な再利用できる署名付きの推薦関係を設計する方針である。

この方針に沿い、推薦そのものにはリポジトリや PR を固定せず、同じ推薦を各リポジトリの受け入れ方針で評価する。ハッカソン版のデータ形式や構成は [ハンドオフ](hackathon-handoff.md)に記した提案であり、既存コードの変更や採用済みのアーキテクチャではない。

### 事前資料の位置づけ

ユーザーは事前の企画検討を進め、実際に使うかどうかは開発着手時に判断する方針。運営への確認は未実施である。公式規約と提出ガイドの記述、作成時期・再利用範囲の記録については [調査結果](hackathon-research.md#募集要項と提出)を参照する。

## 3. 原典と調査状況

### vouch

[mitchellh/vouch](https://github.com/mitchellh/vouch)

README、FAQ、管理 Action、主要な判定実装、MIT ライセンスを確認した。対象は貢献者であり、推薦する権限と参加する資格は別。採否は各プロジェクトが決め、個別 PR の品質保証は行わない。

原典にも別リポジトリの推薦リストを参照する機能がある。Devouch の差分は「共有できること」だけではなく、署名・用途・期限・現在の公開状態を検証できる推薦として持ち運べることに置く。根拠は [調査結果](hackathon-research.md#vouch-が扱っている信頼)。

Ghostty は2026-04-28に GitHub 離脱方針を発表したが、2026-09-22にも vouch の Action 実行成功とリスト更新を確認した。この時点では GitHub への依存の解消は完了していないと判断できる。発表内容・稼働記録・設計への示唆は [Ghostty の調査結果](hackathon-research.md#ghostty-の-github-離脱方針と-vouch-の稼働)にまとめた。

Devouch は原典の設計を参考にしており、vouch 自体を組み込んではいない。現案の推薦対象は GitHub 数値 ID なので、JSON を別のホストへ移せても、移行先のアカウントへの推薦として使う方法は未設計である。複数の GitHub repo 間での再利用と、サービスをまたぐアカウント移行を区別する。

## 4. 企画の中心となる問い

**メンテナーが PR を受け取ったとき、何を根拠にレビューへ進めるか。**

次の二つを分けて設計する。

| 層 | 問い |
|---|---|
| 信頼の入口 | 誰からの貢献を受け付けるか。誰がその人を推薦できるか |
| 変更の来歴 | 誰が作業を委任し、その委任と成果物がどう対応するか |

今回の8時間版では「信頼の入口」を実装する。元の草案の「PR の特定 head commit を人間が引き受ける」方式は採用せず、背景案として残す。委任・Git 来歴の全体検証は、既存版の機能と将来の拡張として区別する。

## 5. 設計原則の候補

以下は企画を具体化するための提案であり、詳細仕様は未確定。

- **人間の確認と信頼を分ける。** 人間であることだけで、誠実さやコード品質を保証しない。
- **判断権を各プロジェクトに置く。** 全世界共通の信用スコアを中心にしない。
- **検証可能性を持ち運べるようにする。** 公開された記録形式と Ruby CLI により、ホストされた画面だけに依存しない検証を目指す。
- **ブロックチェーンの役割を明確にする。** 何を共有・検証するために必要なのか説明できる構成にする。
- **活動量を安易に報酬化しない。** PR・登録・推薦の件数に対する金銭報酬やランキングは初期案に含めない。
- **未検証と悪質を区別する。** Devouch を利用していないことだけで、不正な貢献と判断しない。
- **品質レビューを置き換えない。** 推薦・委任・来歴が検証できても、変更内容の評価は必要である。

Ethereum / ENS のプロトコル、名前の維持、ウォレット、RPC への依存は残る。発行者登録、共通 publisher 鍵、検証サービスの受領証、本文の唯一の保管先を Devouch 運営者へ集めない。World を追加する場合も、proof の要求から検証までの依存を確認する。

## 6. 対象賞

以下は確認した公式 [募集要項](https://ethglobal.com/events/tokyo2026/prizes)と、ユーザーが選択した優先順位に基づく。詳細は [賞別メモ](ethglobal-tokyo-2026-prize-plan.md)を参照する。

### ENS：Best Use of ENSv2

主な候補。総額 $6,000（$3,000 / $2,000 / $1,000）。Sepolia の ENSv2 を中心的に利用し、動作するライブデモと公開コードを用意する。推薦本文と署名の公開、直接の失効、限定したキー権限をデモする。コードの公開時はライセンスを明示する。

### World：条件付きの追加候補

World「Best Use of World ID for Agents」は $7,500。イベントの公式環境での認証、結果の検証、保護操作、失敗経路、統合フィードバックなどが必要。募集要件を満たすことと、Devouch の分散性が保たれることを両方確認する。

現時点で World 統合の成立は未確認。私たちの confidential client と受領証サービスを全員の必須経路にする前案は採用しない。IDKit の公式オンチェーン検証も追加候補だが、要求署名の扱いや対応環境が残る。IDKit を使えば Agents 賞も満たすとは扱わない。

World がなくても基本の推薦フローを完成させ、人間性確認済みとは表示しない。分散性と両立しない場合は World賞への応募を前提にしない。

ENS の Existing Project 賞は Continuity 限定のため対象外。[提出ガイド](https://ethglobal.com/events/tokyo2026/info/details)では最大3パートナーに応募できる。同一パートナー内の複数トラックは1枠と数えるが、重複受賞の保証ではない。

## 7. ハンドオフに記した技術案

具体的な新構成は実装着手時に採用・動作確認する。

| 論点 | 提案 |
|---|---|
| 信頼の対象 | PR を送る管理者またはエージェントのアカウントを GitHub 数値 user ID で識別し、直接推薦する案。推薦者は自分の EOA で署名 |
| 発行する資格 | プロトコル上の公開を運営者の登録で制限しない。受け入れる推薦者は各 repo が決める |
| スマートコントラクト | ENSv2 の既存実装を利用し、独自の推薦台帳を新規実装しない案。推薦者専用 resolver のデプロイ・初期化は必要 |
| 公開と失効 | 推薦者が、自分で管理する ENS 名・専用 resolver へウォレットから直接書く |
| 保存先 | 公開本文と署名は ENS。配布用コピーと repo 方針は各 repo の `.devouch/` 内の JSON |
| CLI・Action・Web | Ruby CLI が検証・採否を判断。Action は同じ検証を PR 作者に対して実行。静的 Web は署名と直接操作を補助 |
| 更新権限 | 推薦者が必要に応じて自分の補助鍵へ指定キーのみ委任。共通の運営者鍵を置かない |
| 再利用 | 同じ推薦 JSON を二つの repo 方針で評価。Git でコピーしても再署名・chain 書き込みは不要 |
| 人間性 | 基本構成では未確認。World は独立した検証と運営者不在の操作が両立する場合のみ追加 |
| 負担 | 本文保存のガス、公開履歴、名前の維持、鍵管理、RPC の可用性 |

暗号処理は既存ライブラリを使う。JSON 本文はアプリ上限4 KiBを目安に実ガスを確認する案であり、ENS 標準の上限ではない。本文・推薦関係は撤回後も公開履歴に残る。ローカルの例には合成 ID を使え、実 PR の照合には公開範囲を理解したテスト参加者の GitHub ID を使う。

CLI を直接使う手順、4コマンドの引数、JSON 出力、終了コードは [CLI インターフェース設計](cli-interface.md)にまとめた。取得・検証は CLI 単体で行い、推薦案・失効案の署名と送信は静的 Web / ウォレットへ渡す案である。

ENS が提供する記録・権限と、CLI が実装する推薦の検証・採否を区別する。独自コントラクトを書かずに使う場合の初期準備と、専用コントラクトを検討する条件は [既存コントラクトの利用とデプロイ](hackathon-data-model.md#既存コントラクトの利用とデプロイ)にまとめた。

## 8. 最小実装の方針

一人の推薦者、一つの用途、二つの repo 方針を使い、同時に有効な推薦は一人への一件に絞る。管理者名義の発行・実 fork PR・失効を確認した後、エージェント名義へ新しく発行して同じ流れを繰り返す。各名義で有効時の Action と、失効後の再実行を確認する。これは順番に二つの名義を試す計画であり、複数推薦を同時保持する機能ではない。実在 OSS への導入実績には見せない。

- 推薦者が直接公開・失効でき、私たちの承認 API を必要としない。
- 別の利用者が ENS から本文を取得し、署名・現在値・履歴・期限を検証できる。
- 有効な証拠と repo の採否を分け、失効後は双方で不採用になる。
- 補助鍵への限定権限と権限外拒否、管理者の直接回復経路を示す。
- 私たちの公開サイトを止め、ローカル配布物と別の RPC で取得・公開・失効を行えることを確認する。
- メンテナーは policy と workflow の2ファイル、貢献者は初回に推薦 JSON を1ファイル追加する導入案を検証する。ウォレット・手動 secret・DB・常設サーバーを導入者の必須条件にしない。
- 実際の fork PR で作者の数値 ID と推薦を照合し、base commit の方針で評価して Summary に表示する。PR のコードは実行しない。

委任・Git 全履歴、全推薦の検索、複数組織の交渉、自動マージ、トークン報酬は必須範囲に入れない。World を省く場合は、人間性未確認を明示する。

最初の Action は推薦結果の表示用とする案。required check による強制運用は含めない。GitHub の PR 内で workflow が変更される境界と、ENS の失効が過去の check を自動更新しない制約がある。

現状の一記録・一推薦では、同じキーへの追加発行が前の推薦を失効させる。Git に複数ファイルを置くだけでは解決しないため、一般の OSS で複数人を推薦する構成は別途設計する。resolver の設定負担も残る。[導入マニュアルの残課題](adoption-guide.md#このマニュアルから見える残課題)を確認して、導入の手軽さを判断する。

送信側の手順は [AI エージェント管理者向けマニュアル](agent-operator-guide.md)でレビューする。ユーザーは管理者本人名義とエージェント自身のアカウント名義の両方を利用要件として明示した。マニュアルは実際の PR 作者へ直接推薦を付ける案で、両方の手順を整理した。管理者への推薦の継承や管理関係の証明は別の論点であり、委任の追加を決定したものではない。

## 9. 当日の時間配分案

細かな入出力と完了条件は [ハンドオフ](hackathon-handoff.md#8時間の実行順序)に記載した。

| 時間 | 作業 |
|---|---|
| 実装 0〜1.5時間 | 環境確認、ENS の直接操作・権限・本文サイズとガス |
| 実装 1.5〜4時間 | 署名・公開、CLI の取得・検証、二つの方針 |
| 実装 4〜5時間 | 直接失効・履歴、旧推薦の復活拒否 |
| 実装 5〜6.25時間 | Action の梱包、repo の JSON・PR 作者の取得、CI 用推薦の新規発行、導入手順の実行 |
| 実装 6.25〜8時間 | 静的画面・ローカル配布、運営者不在・別 RPC、両送信名義・失効後の CI、修正・手順 |
| 提出素材 4時間 | README、構成図、動画、要件照合、提出 |
| ピッチ 4時間 | 主張・台本・スライド・練習・本番 |

2時間時点で ENS の基本操作が通らなければ、未達条件と原因を報告する。中央サービスへの置換やモックを、分散した経路の完成として扱わない。World の追加統合で必須経路の完成を遅らせない。

Action を必須に加えた分、静的 UI の仕上げ枠を縮めた見積もり。両送信名義の通し確認を含め、8時間で成立するかは未測定。提出・ピッチの時間で実装超過を吸収しない。
