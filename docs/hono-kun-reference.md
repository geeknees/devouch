## 図から読み取れるフロー

1. コントリビューターが PR を作成する。
2. Hono-kun が PR を評価する。
3. 良い PR はレビューへ進める。
4. 品質が低い、文脈を踏まえていない、または不審な PR は、理由付きで閉じる。
5. 閉じた PR が扱う問題が実在する場合、Hono-kun が代替 PR を作成してレビューへ進める。

参考になるのは、**問題提起の価値と、提出された実装を採用するかを分けている点**である。実装を採用しなくても、解決すべき問題は引き継げる。

## Devouch との関係

既存版の Devouch は、人間からエージェントへの委任と Git の来歴を検証する Ruby CLI / GitHub Action である。以下はその機能を使う将来の利用例で、今回の推薦中心の8時間版の実装範囲ではない。

Hono-kun のようなフローでは、外部から提出された実装を評価した後、プロジェクト側のエージェントに代替実装を任せる場面がある。ここが Devouch の利用候補になる。

| 場面 | Hono-kun の図が示す役割 | Devouch が担いうる役割 |
|---|---|---|
| 外部 PR の評価 | 品質・文脈・不審さを評価する | 委任・来歴の検証結果を判断材料として提供する |
| 代替 PR の作成 | エージェントが実装する | 人間からの委任と生成された変更の関係を検証する |
| レビュー | 元の PR または代替 PR を確認する | 委任と来歴をレビュアーが確認できるようにする |

この役割分担は提案であり、現在の連携や対応機能を示すものではない。

## 検討する利用シナリオ

1. メンテナーが、外部 PR の問題提起を採用する。
2. メンテナーが、代替実装をエージェントに委任する。
3. エージェントが代替 PR を作成する。
4. Devouch が委任と Git の来歴を検証する。
5. レビュアーが、検証結果と実装内容を確認する。

元の PR への参照と貢献者のクレジットを残すことも、この利用例の要件候補とする。

## 設計上の境界とトレードオフ

**委任・来歴の検証は、品質や善意を保証しない。** 検証に成功した変更でも、内容のレビューは必要である。また、検証情報がない外部 PR を、それだけで低品質・不審と判定するべきではない。

メンテナーにはレビュー負担を軽減する利点がある。一方、投稿者には、自分の PR が閉じられて代替実装に置き換わることで、貢献が軽視されたと感じる可能性がある。これは図から確認できる事実ではなく、運用上考慮すべき懸念である。理由の説明、元の提案への参照、クレジットの保持が重要になる。

PR の自動クローズや代替実装の開始条件は、権限とプロジェクト方針に関わる。Devouch の検証結果だけで、それらの操作を許可する設計にはしない。

## 未決事項

- 委任の対象範囲と、生成された変更をどう対応づけるか。
- 検証不能と検証失敗を、レビュー画面でどう区別するか。
- 元の PR・問題提起・代替 PR の関係をどこに記録するか。
- 既存の Devouch の機能で、この利用例をどこまで表現できるか。

## 次の確認

既存実装と照合し、まずは人間が明示的に代替実装を委任する小さな利用例を検討する。委任と来歴がレビュー時に理解できるかを確認し、自動評価・自動クローズの導入判断は別途行う。
